# Core Backend

Мероприятия, записи, лист ожидания и расписание напоминаний. Бот MAX — канал
доставки: Core Backend решает, **что** и **когда** сказать пользователю, и
отвечает боту, когда пользователь нажал кнопку.

```
мини-приложение ──► Core Backend ──POST /api/v1/notifications──► бот ──► MAX
                        ▲                                          │
                        └──── POST /registrations/{id}/confirm ◄───┘  (нажатие кнопки)
```

Go 1.24, SQLite (один файл, ставить ничего не нужно), без фреймворков.

## Что готово

| | |
|---|---|
| Правила записи | места, лист ожидания, окно подтверждения 6 ч, закрытие записи за 1 ч, предложение освободившегося места с таймером, отмена с причиной — перенесено из `frontend/src/api/mocks/handlers.js` |
| Все 8 уведомлений бота | `registration_created`, `reminder_24h`, `confirmation_required`, `confirmation_retry`, `reminder_1h`, `waitlist_offer`, `event_updated`, `event_cancelled` |
| Планировщик | напоминания по времени, истечение предложений; каждое сообщение уходит ровно один раз (ключ дедупликации в базе), перенос мероприятия заново взводит напоминания |
| Доставка | outbox: уведомление пишется в одной транзакции с изменением, потом доставляется; повтор при 5xx, 422 от бота → пользователь помечается «бот недоступен» |
| Пять эндпоинтов для бота | `confirm`, `cancel`, `accept`, `decline`, `bot-status` — с правилами доверия из `bot/docs/INTEGRATION_MINIAPP.md` §6.1 |
| Проверка в одиночку | `/dev/*`: вход без MAX, перевод часов, демо-участники; `TIMING_PRESET=fast` |
| Все пути мини-приложения | вход через `initData` (подпись проверяет SDK MAX, плюс срок `INITDATA_MAX_AGE`), профиль, согласие, интересы, каталог с фильтрами, «Мои записи», «Мои мероприятия», отчёт организатора, просмотры, жалобы, «Для вас», подсказка тегов. Формы ответов сверены с моками фронтенда автоматически |
| Демо-данные | пустая база наполняется 16 мероприятиями и записями из моков (`SEED_DEMO=true`), даты считаются от момента запуска. Боту демо-людям ничего не отправляется |

**Верификация номера** (`POST /me/verification`). MAX подписывает контакт из
`WebApp.requestContact()` полями `auth_date` и `hash`, но как считается этот
`hash`, нигде не описано, а проверять по догадке нельзя. Сейчас
достаточно непустого номера от сессии, прошедшей проверку `initData`.
Когда MAX опишет подпись контакта, проверку нужно добавить в
`service.Verify`.

## Запуск

Вся система поднимается из корня репозитория, настройки — один общий `.env`
там же (см. корневой `README.md`):

```bash
make env && make up        # Docker: мини-приложение, Core Backend, бот
make run-core              # или без Docker, только Core Backend
```

Без Docker нужен Go 1.24 и **gcc**: SQLite-драйвер собирается через cgo.
На Ubuntu, если `go run` пишет `C compiler "gcc" not found`:
`sudo apt install -y gcc`. В Docker-образе всё есть.

Ключи между сервисами задаются в `.env` по одному разу, backend читает те
же имена, что и бот: `INTERNAL_API_KEY` (backend → бот) и `CORE_API_KEY`
(бот → backend). Имена `BOT_INTERNAL_API_KEY` / `BOT_API_KEY` тоже
понимаются — на случай запуска backend отдельно.

## Как проверить в MAX одному и без ожидания

В корневом `.env`: `MAX_MODE=real`, `MAX_BOT_TOKEN`, `DEV_MODE=true`,
`DEMO_MAX_USER_ID=<ваш max_user_id>`. Система запущена (`make up`). Дальше
из корня:

```bash
make scenario
```

Скрипт играет организатора и двигает часы backend вперёд. Вы в MAX получаете
по очереди: «Вы записаны» → напоминание за сутки → «Подтвердите участие»
(нажимаете «Приду», скрипт проверяет, что backend это получил) → «Скоро
начало» → «Освободилось место» (нажимаете «Занять место») → «Мероприятие
изменено» → «Мероприятие отменено». Минуты три.

Без MAX и без токена ту же цепочку проверяет автотест с ботом в mock-режиме:

```bash
make e2e      # из корня; 19 проверок, Docker не нужен
```

### Инструменты `/dev` (только `DEV_MODE=true`)

| Запрос | Что делает |
|---|---|
| `POST /dev/login` `{"max_user_id": 123, "first_name": "Анна"}` | Вход без MAX → `{token}`. Без `max_user_id` — демо-участник, ему ничего не отправляется |
| `POST /dev/clock` `{"advance": "23h30m"}` / `{"set": "2026-09-29T13:00:00+03:00"}` / `{"reset": true}` | Сдвинуть часы backend и сразу прогнать планировщик. В ответе — что ушло боту |
| `POST /dev/scheduler/run` | Прогнать планировщик сейчас |
| `POST /dev/events/{id}/fill` `{"count": 3}` | Занять места демо-участниками |
| `POST /dev/registrations/{id}/cancel` | Отменить запись от имени владельца — освободить место для очереди |
| `GET /dev/state?payload=1` | Мероприятия, записи, очередь уведомлений с телами запросов к боту |
| `POST /dev/reset` | Очистить базу |

Часы сдвигаются только для правил (напоминания, окна, таймеры предложений).
Сессии и повторы доставки идут по настоящему времени.

`TIMING_PRESET=fast` в `.env` — второй способ: все интервалы в
минутах. Мероприятие через 12 минут пройдёт всю цепочку напоминаний в
реальном времени.

## API

Все пути доступны и от корня (так их зовёт бот), и под `/api` (так их зовёт
мини-приложение по умолчанию). Ошибки — `{"error": {"code", "message", "request_id", "details"}}`,
коды те же, что понимают бот и `frontend/src/api/errors.js`. Время — RFC 3339 со
смещением города (`+03:00`), UTC во входе отвергается.

| Метод и путь | Кто зовёт | |
|---|---|---|
| `POST /registrations/{id}/confirm` | бот, мини-приложение | «Приду» |
| `POST /registrations/{id}/cancel` | бот, мини-приложение | отказ; `cancel_reason`: `ill`, `plans_changed`, `other` |
| `POST /waitlist-offers/{id}/accept` | бот, мини-приложение | «Занять место»; поздно → `410 offer_expired` |
| `POST /waitlist-offers/{id}/decline` | бот, мини-приложение | «Отказаться» |
| `POST /max-users/{max_user_id}/bot-status` | бот | может ли бот писать пользователю |
| `POST /registrations` `{event_id}` | мини-приложение | запись или очередь → 201 |
| `POST /events`, `GET/PATCH /events/{id}` | мини-приложение | создание, карточка, правка (правка времени/адреса/названия → `event_updated`) |
| `POST /events/{id}/cancel`, `POST /events/{id}/messages` | мини-приложение | отмена, сообщение участникам |
| `POST /auth/max` `{init_data}` | мини-приложение | вход → `{token, user}`; в `DEV_MODE` `init_data: "dev"` — демо-пользователь Пётр Смирнов |
| `GET/PATCH /me`, `POST /me/verification`, `POST /me/consent`, `GET/PUT /me/interests` | мини-приложение | профиль |
| `GET /me/registrations`, `GET /me/events` | мини-приложение | «Мои записи», «Мои мероприятия» |
| `GET /events?city_id&q&category_id&tag_ids&date&daypart&district&has_seats&sort&page&page_size` | все | каталог, без сессии тоже |
| `GET /events/{id}/report` | автор | отчёт |
| `POST /events/{id}/views`, `POST /events/{id}/complaints` | мини-приложение | |
| `GET /recommendations?city_id`, `POST /ml/suggest-tags` | мини-приложение | «Для вас», подсказка тегов |
| `GET /categories`, `GET /health` | все | |

**Кто есть кто.** Бот приходит с `X-Api-Key` и действует за `max_user_id` из
тела: он взял его из события MAX. Мини-приложение приходит с
`Authorization: Bearer <сессия>`, и `max_user_id` в теле обязан совпасть с
сессией, иначе `403`. Повтор запроса с тем же `request_id` возвращает
сохранённый ответ.

## Устройство

```
cmd/core/            точка входа: HTTP, планировщик, доставка
internal/domain/     модель, статусы, коды ошибок, города, категории, расписание
internal/store/      SQLite: схема и запросы; одно соединение — транзакции не гоняются
internal/service/    правила: записи, очередь, события, планировщик, dev-инструменты
internal/notify/     доставка outbox → бот, повторы, 422
internal/httpapi/    маршруты, два режима доверия, идемпотентность, /dev
scripts/             e2e-with-bot.sh (автотест), scenario.sh (проверка в MAX)
```
