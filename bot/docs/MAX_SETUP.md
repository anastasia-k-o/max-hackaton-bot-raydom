# Настройка MAX: токен, webhook, переход из mock в real

Документ для разработчика и DevOps. Всё, что касается протокола MAX, сверено с
официальным Go SDK `github.com/max-messenger/max-bot-api-client-go/v2` (тег
v2.4.0) и его `schema.yaml`.

Официальная документация: <https://dev.max.ru/>

---

## 1. Проверенные факты о MAX Bot API

Это не пересказ по памяти, а то, что зафиксировано в исходниках SDK и схеме
API. Если MAX что-то поменяет, документация MAX имеет приоритет.

| Что | Значение | Где зафиксировано |
|---|---|---|
| Хост API | `https://platform-api2.max.ru` | `const.go`, `DefaultHostV2` |
| Старый хост | `platform-api.max.ru` — **устарел**, помечен «not allowed» | `const.go`, `DefaultHost` |
| Аутентификация | заголовок `Authorization: <токен>` — **без** префикса `Bearer` | `client.go` |
| Заголовок секрета webhook | `X-Max-Bot-Api-Secret` | `const.go`, `SecretHeader` |
| Профиль бота | `GET /me` | `const.go`, `pathMe` |
| Отправка сообщения | `POST /messages?user_id=<id>` | `messages.go` |
| Правка сообщения | `PUT /messages?message_id=<mid>` | `messages.go` |
| Ответ на кнопку | `POST /answers?callback_id=<id>` | `messages.go` |
| Подписка на webhook | `POST /subscriptions` | `subscriptions.go` |
| Клавиатура | вложение `type: "inline_keyboard"`, `payload.buttons: [][]Button` | `model/keyboard.go` |
| Лимит payload кнопки | **1024 байта** | `schema.yaml`, `CallbackButton.payload` |
| Лимит deep-link payload | 128 символов | `schema.yaml` |
| Превышение лимита запросов | HTTP **429** | `schema.yaml` |
| **Порты для webhook** | **80, 8080, 443, 8443, 16384–32383** | `schema.yaml`, описание `POST /subscriptions` |

Два момента, на которых чаще всего спотыкаются:

1. **Никакого `Bearer`.** Токен идёт в `Authorization` как есть.
2. **Порт webhook ограничен списком.** MAX не станет доставлять события на
   произвольный порт. Это про публичный адрес, который вы регистрируете, —
   сам бот внутри может слушать что угодно, если перед ним стоит reverse proxy.

Типы событий (`model/types.go`), из которых бот подписывается на три:

```
bot_started, message_created, message_callback   ← используются ботом
message_edited, message_removed, bot_added, bot_removed, user_added,
user_removed, bot_stopped, dialog_cleared, dialog_removed, dialog_muted,
dialog_unmuted, chat_title_changed, comment_created, comment_edited,
comment_removed
```

Неизвестные и неподписанные типы бот подтверждает и игнорирует — паники не
будет.

## 2. Получение токена

1. Откройте в MAX диалог с **[@MasterBot](https://max.ru/MasterBot)**.
2. Следуйте инструкциям, создайте бота.
3. MasterBot пришлёт токен. Сохраните его — это и есть `MAX_BOT_TOKEN`.

Токен даёт полный доступ к боту. В git его не коммитить: `.env` уже в
`.gitignore`, а `.env.example` содержит только пустые значения.

## 3. Переменные окружения

```env
MAX_MODE=real
MAX_BOT_TOKEN=<токен от @MasterBot>
MAX_WEBHOOK_SECRET=<придуманная вами случайная строка>
```

`MAX_WEBHOOK_SECRET` вы придумываете сами и передаёте его же в
`POST /subscriptions`. MAX будет присылать это значение в заголовке
`X-Max-Bot-Api-Secret` при каждом вызове webhook, а бот — сверять.

Сгенерировать:

```bash
openssl rand -hex 32
```

**Не путайте с `INTERNAL_API_KEY`.** Это разные механизмы:

| Переменная | Кто кого вызывает | Заголовок |
|---|---|---|
| `MAX_WEBHOOK_SECRET` | MAX → Bot | `X-Max-Bot-Api-Secret` |
| `INTERNAL_API_KEY` | Core Backend → Bot | `X-Internal-Api-Key` |

Полный список переменных с комментариями — в [`.env.example`](../.env.example).

## 4. Проверка токена

### При старте бота — автоматически

В `MAX_MODE=real` бот выполняет `GET /me` до того, как начнёт принимать
трафик. Если токен недействителен, процесс **не стартует**:

```
startup failed: MAX rejected the bot token.
  Check MAX_BOT_TOKEN in your .env: it should be the token @MasterBot sent you.
  Underlying error: max get_me: max: unauthorized (check MAX_BOT_TOKEN)
```

Это сознательное решение: работать дальше с заведомо сломанной конфигурацией
и выяснять это по одному упавшему уведомлению за раз — хуже, чем упасть сразу.

Если же MAX просто недоступен (сеть, таймаут), бот стартует и пишет
предупреждение — такая проблема может пройти сама, а отказ от запуска во время
кратковременного сбоя был бы отдельным видом отказа.

При успехе в логе будет:

```json
{"level":"INFO","msg":"max token verified","bot_user_id":4242,"bot_username":"afisha_bot","bot_name":"Афиша"}
```

### Вручную

```bash
curl -s https://platform-api2.max.ru/me \
  -H "Authorization: $MAX_BOT_TOKEN" | jq
```

Ожидаемый ответ:

```json
{
  "user_id": 4242,
  "first_name": "Афиша",
  "username": "afisha_bot",
  "is_bot": true
}
```

### Через readiness-пробу бота

```bash
curl -s localhost:8080/ready | jq
```

```json
{
  "status": "ready",
  "dependencies": [
    { "name": "max",  "mode": "real", "status": "ok" },
    { "name": "core", "mode": "stub", "status": "ok" }
  ]
}
```

При проблеме с токеном — `503` и `"status": "error"` с кратким описанием.
Токен в этот вывод не попадает.

## 5. Требования к HTTPS и портам

MAX доставляет webhook только на **HTTPS** и только на порты **80, 8080, 443,
8443 или 16384–32383**.

### Локальная разработка: туннель

Самый быстрый путь — ngrok:

```bash
ngrok http 8080
```

Вы получите адрес вида `https://a1b2c3d4.ngrok-free.app`. URL webhook будет:

```
https://a1b2c3d4.ngrok-free.app/webhooks/max
```

Подойдёт любой аналог: cloudflared, localtunnel, bore.

Учтите: бесплатный ngrok выдаёт новый адрес при каждом запуске, и подписку
придётся переоформлять.

### Боевой контур

Reverse proxy (nginx, Caddy, Traefik) с валидным TLS-сертификатом перед ботом.
Бот внутри может слушать любой порт — ограничение относится к публичному
адресу.

Минимальный nginx:

```nginx
server {
    listen 443 ssl;
    server_name bot.example.ru;

    ssl_certificate     /etc/letsencrypt/live/bot.example.ru/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/bot.example.ru/privkey.pem;

    location /webhooks/max {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        # Заголовок секрета должен дойти до бота в неизменном виде.
        proxy_pass_request_headers on;
    }

    # Остальные пути наружу не публикуем:
    # /api/v1/* доступен только Core Backend во внутренней сети,
    # /dev/* в production не существует вовсе.
}
```

## 5a. Long polling: работа без публичного адреса

Раздел 5 описывает, как сделать бота достижимым снаружи. Этот раздел — о том,
как обойтись без этого вовсе.

### Зачем

Webhook требует, чтобы MAX мог постучаться к нам. На ноутбуке за NAT
публичного адреса нет, поэтому обычный выход — туннель. Туннель — это
сторонний сервис, аккаунт, и ещё одна точка отказа ровно там, где её не ждут:
у ngrok требуется регистрация, у cloudflared исходящий QUIC блокируется во
многих сетях.

Long polling разворачивает направление. Бот сам открывает соединение к MAX и
держит его, ожидая событий; MAX отвечает, когда событие появляется, или по
истечении таймаута. Входящий адрес не нужен вообще.

### Режимы взаимоисключающие

В схеме MAX про `GET /updates` сказано прямо: метод предназначен для бота,
который **не подписан** на webhook. Если подписка существует, события уйдут на
неё, а опрос будет возвращать пустоту — и ни одной ошибки при этом нигде не
появится.

Бот проверяет это при старте и предупреждает:

```
WARN у бота есть активные подписки на webhook, а режим — polling;
     события будут уходить на webhook, и опрос вернёт пустоту
     subscriptions=[https://a1b2c3d4.ngrok-free.app/webhooks/max]
```

Это предупреждение, а не отказ стартовать: токен может быть общим на несколько
команд, и снимать чужую подписку бот не станет. Решение за вами — раздел 6,
«Удаление подписки».

### Настройка

```diff
-MAX_UPDATES_MODE=webhook
+MAX_UPDATES_MODE=polling
```

Всё. `MAX_WEBHOOK_SECRET` в этом режиме не требуется, публичный адрес не
требуется, туннель не требуется.

Параметры опроса (необязательные, значения по умолчанию разумны):

| Переменная | По умолчанию | Границы (схема MAX) | Что делает |
|---|---|---|---|
| `MAX_POLL_TIMEOUT` | `30` | 0..90 | секунд удержания соединения в ожидании событий |
| `MAX_POLL_LIMIT` | `100` | 1..1000 | максимум событий в одном ответе |

Значение за границей отвергается при старте, а не исправляется молча: тихая
правка прячет опечатку до момента, когда режим переключат.

### Что меняется в поведении бота

Ничего. Событие проходит через тот же `maxapi.DecodeUpdate` и тот же
`BotService.HandleUpdate`, что и тело webhook. Это проверяется тестом
`TestPollingAndWebhookAgree`: одно и то же событие, поданное двумя
транспортами, обязано дать одинаковое действие в Core Backend.

Что меняется в HTTP-поверхности:

- при `MAX_MODE=real` и `MAX_UPDATES_MODE=polling` маршрут `POST /webhooks/max`
  **не поднимается** и отдаёт 404. Секрет в этом режиме не требуется, значит
  проверять подпись было бы нечем, а открытый эндпойнт, принимающий «события
  от MAX», позволил бы кому угодно подтвердить чужую регистрацию;
- при `MAX_MODE=mock` маршрут остаётся в любом режиме: через него Postman и
  `make smoke` подают боту события, и это единственный способ прогнать полный
  цикл без сети;
- `GET /ready` сообщает режим в поле `updates_mode`.

### Проверка, что опрос идёт

```bash
curl -s localhost:8080/ready | jq '.updates_mode'
```

```
"polling"
```

В логах при старте:

```
INFO режим получения событий: polling (публичный адрес не нужен)
INFO подписок на webhook нет — режим polling применим
INFO polling started timeout_seconds=30 limit=100
```

Дальше — тишина до первого события. Пустой опрос ничего не пишет в лог
намеренно: при `MAX_POLL_TIMEOUT=30` это две строки в минуту круглосуточно, в
которых нет никакой информации.

### Как это устроено внутри

`marker` — позиция в потоке событий. Важная деталь семантики MAX: **передача
`marker` фиксирует все предыдущие события**. Отдельного «подтвердить
обработку» в API нет — подтверждением служит сам следующий запрос. При первом
запросе параметр не передаётся: это означает «отдай всё, что накопилось с
последней фиксации», и это не то же самое, что `marker=0`.

Отсюда два решения, которые стоит знать:

- **неудачный опрос не двигает `marker`.** Пачка не получена, фиксировать
  нечего. Пауза между попытками растёт от 1 до 30 секунд;
- **`marker` двигается после обработки пачки, даже если какое-то событие
  обработать не удалось.** Соблазнительная альтернатива — не двигать до
  успеха — на деле хуже: сбой на одном событии остановил бы весь поток, а
  повторная выдача всё равно была бы отброшена как дубликат (бот помнит
  обработанные `callback_id`). Получился бы бот, который встал навсегда и
  ничего при этом не переобработал.

Неверный токен (401) — единственная ошибка, при которой опрос не повторяется:
процесс останавливается с сообщением, называющим `MAX_BOT_TOKEN`. Повторять
401 значит крутить бесконечный цикл с заранее известным результатом.

### Ограничения

- Одно соединение — один процесс. Две реплики с одним токеном будут
  растаскивать события друг у друга: каждая зафиксирует то, что забрала.
  Для боевого контура с несколькими репликами нужен webhook;
- события забираются по одному соединению последовательно, без параллелизма.
  Для хакатонной нагрузки этого с запасом, для заметного потока — нет.

Проще говоря: polling — для разработки и демонстрации, webhook — для боевого
контура. Переключение между ними — одна строка в `.env`.

## 5b. Кнопка «Открыть афишу»: ссылка или open_app

Кнопка под сообщением может открывать мини-приложение двумя способами. Способ
выбирается переменной `MAX_MINIAPP_BUTTON`.

| Значение | Где откроется | `initData` | Что нужно |
|---|---|---|---|
| `link` (по умолчанию) | в браузере | нет | `MINI_APP_URL` или `event.mini_app_url` |
| `open_app` | внутри MAX | есть | мини-приложение привязано к боту в MAX |

**Почему это важно.** Мини-приложение узнаёт пользователя по `initData`,
которую передаёт ему MAX. Обычная ссылка открывается в браузере, где
`initData` нет: в режиме моков фронт это переживёт (у него демо-вход), а в
боевом покажет «Откройте афишу в MAX». Кнопка `open_app` открывает
мини-приложение внутри мессенджера, и id мероприятия приходит в него как
стартовый параметр — фронт по нему сразу открывает карточку.

**Почему по умолчанию выключено.** Кнопка `open_app` ссылается на
мини-приложение, привязанное к боту. Если привязки нет, MAX может отвергнуть
сообщение целиком, и тогда не дойдёт ни одно уведомление. Привязку делает
владелец токена — в нашем случае организаторы хакатона. Включайте
`MAX_MINIAPP_BUTTON=open_app` только после того, как они подтвердят, что адрес
мини-приложения указан в настройках бота.

При старте бот предупреждает в логе, что `open_app` включён. Если после этого
уведомления перестали доходить, верните `MAX_MINIAPP_BUTTON=link` и
перезапустите.

Настраивать id бота не нужно: для кнопки нужны его `user_id` и `username`, и
бот берёт их из `GET /me` при старте. Пока `GET /me` не прошёл (например, MAX
был недоступен в момент запуска), такие кнопки уходят обычными ссылками.

Формат адреса. Мини-приложение открывает карточку по пути `/app/{event_id}`,
поэтому `MINI_APP_URL` задаётся с `/app` на конце:
`MINI_APP_URL=https://<хост>/app`.

## 6. Регистрация webhook

```bash
curl -X POST https://platform-api2.max.ru/subscriptions \
  -H "Authorization: $MAX_BOT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://bot.example.ru/webhooks/max",
    "secret": "'"$MAX_WEBHOOK_SECRET"'",
    "update_types": ["bot_started", "message_created", "message_callback"],
    "version": "0.0.1"
  }'
```

Ответ:

```json
{ "success": true }
```

`update_types` — ровно те три типа, которые бот обрабатывает. Можно не
указывать вовсе (тогда придут все), но точный список экономит трафик и
делает намерение явным.

### Проверка подписки

```bash
curl -s https://platform-api2.max.ru/subscriptions \
  -H "Authorization: $MAX_BOT_TOKEN" | jq
```

```json
{
  "subscriptions": [
    {
      "url": "https://bot.example.ru/webhooks/max",
      "time": 1758556800000,
      "update_types": ["bot_started", "message_created", "message_callback"],
      "version": "0.0.1"
    }
  ]
}
```

Секрет в этом ответе не возвращается — это нормально.

### Удаление подписки

```bash
curl -X DELETE "https://platform-api2.max.ru/subscriptions?url=https://bot.example.ru/webhooks/max" \
  -H "Authorization: $MAX_BOT_TOKEN"
```

Пригодится при смене адреса ngrok: старую подписку стоит снять, иначе MAX
будет пытаться достучаться до мёртвого туннеля.

## 7. Переход из mock в real

Бизнес-код не меняется. Меняется `.env`.

### Шаг 1. Убедитесь, что mock-режим работает

```bash
make smoke
```

Все проверки должны быть зелёными. Если что-то не так здесь, в real-режиме
проще не станет.

### Шаг 2. Правка `.env`

```diff
-MAX_MODE=mock
+MAX_MODE=real
-MAX_BOT_TOKEN=
+MAX_BOT_TOKEN=<токен от @MasterBot>
-MAX_WEBHOOK_SECRET=
+MAX_WEBHOOK_SECRET=<сгенерированная строка>
```

`MAX_WEBHOOK_SECRET` нужен только при `MAX_UPDATES_MODE=webhook`. Если
публичного адреса нет, пропустите его и сразу переходите к разделу 5a.

`CORE_MODE=stub` оставьте: настоящий MAX и заглушка Core — рабочая и очень
полезная комбинация. Вы увидите реальные сообщения в мессенджере, а действия
будут складываться в `/dev/core/actions`.

### Шаг 3. Перезапуск и проверка

```bash
make run
curl -s localhost:8080/ready | jq
```

Дождитесь `"mode": "real", "status": "ok"`.

### Шаг 4. Входящие события: выберите одно из двух

**Вариант А — polling (проще, публичный адрес не нужен):**

```diff
-MAX_UPDATES_MODE=webhook
+MAX_UPDATES_MODE=polling
```

и перезапустить. Туннель и подписка не нужны. Подробности — раздел 5a.

**Вариант Б — webhook (нужен публичный HTTPS-адрес):**

```bash
ngrok http 8080
# затем POST /subscriptions с полученным https-адресом (раздел 6)
```

При этом в `.env` должен быть задан `MAX_WEBHOOK_SECRET` — тот же, что вы
передаёте в `POST /subscriptions`.

### Шаг 5. Отправьте себе сообщение

Нужен ваш `max_user_id`. Самый простой способ узнать: напишите боту что-нибудь
в MAX и посмотрите в логи бота — там будет `max_user_id`.

Дальше проще всего прогнать все восемь типов уведомлений одной командой:

```bash
bash scripts/demo.sh <ваш_max_user_id>
```

Скрипт играет роль Core Backend: он вызывает `POST /api/v1/notifications` тем
же контрактом, которым потом будет пользоваться настоящий бэкенд. Для каждого
уведомления он печатает, что именно должно прийти в MAX, — это и есть критерий
приёмки. Мини-приложение не требуется: если `MINI_APP_URL` пуст, кнопка-ссылка
просто не добавляется к сообщению.

Вторая половина цикла — то, что бот передал бы в Core Backend при нажатии
кнопок:

```bash
bash scripts/demo.sh --watch
```

Ниже — тот же вызов вручную, если нужно послать одно конкретное тело.

```bash
curl -X POST localhost:8080/api/v1/notifications \
  -H 'Content-Type: application/json' \
  -H "X-Internal-Api-Key: $INTERNAL_API_KEY" \
  -d '{
    "request_id": "req_real_1",
    "type": "confirmation_required",
    "recipient": {"max_user_id": ВАШ_ID},
    "event": {
      "id": "event_42",
      "title": "Йога в парке",
      "starts_at": "2026-09-22T19:00:00+03:00",
      "address": "Парк Горького",
      "mini_app_url": "https://afisha.example.ru/app/event_42"
    },
    "registration": {"id": "registration_15"}
  }'
```

Сообщение с кнопками «Приду» и «Не смогу» придёт в MAX. Нажмите кнопку —
сообщение должно смениться на «✅ Участие подтверждено», а в
`GET /dev/core/actions` появится запись.

Подробный разбор этого сценария — в [POSTMAN.md](POSTMAN.md), сценарий 3.

### Возврат в mock

`MAX_MODE=mock` и перезапуск. Токен можно не убирать — в mock-режиме он не
используется.

## 8. Rate limits

MAX сигнализирует о превышении кодом **429**. Конкретные пороги в схеме не
зафиксированы и могут меняться — сверяйтесь с актуальной документацией
<https://dev.max.ru/>.

Что делает бот:

- SDK сам выполняет до 3 повторов с экспоненциальной задержкой на отправке
  сообщений;
- адаптер помечает 429 как временную ошибку, поэтому пользователь видит
  «попробуйте ещё раз», а кнопки остаются активными;
- на каждый вызов установлен таймаут (`MAX_TIMEOUT`, по умолчанию 10 секунд),
  бесконечных ожиданий нет.

Брокер сообщений для сглаживания нагрузки намеренно не вводился: для MVP это
сложность без соответствующей пользы. Если упрётесь в лимит при массовой
рассылке, правильное место для очереди — Core Backend, который эту рассылку
инициирует.

## 9. Troubleshooting

### Бот не стартует: «MAX rejected the bot token»

Токен неверный, просрочен или отозван. Проверьте вручную:

```bash
curl -i https://platform-api2.max.ru/me -H "Authorization: $MAX_BOT_TOKEN"
```

Частые причины: лишние пробелы или перевод строки в `.env`, случайно
добавленный префикс `Bearer`, скопирована только часть токена.

### Webhook не приходит

Пройдите по списку:

1. **Подписка существует?**
   `curl -s https://platform-api2.max.ru/subscriptions -H "Authorization: $MAX_BOT_TOKEN"`
2. **URL доступен извне?**
   `curl -i https://ваш-адрес/webhooks/max -X POST -d '{}'` — ожидается 401
   (секрет не передан), но **не** таймаут и не 404.
3. **HTTPS настоящий?** Самоподписанный сертификат MAX не примет.
4. **Порт из разрешённого списка?** 80, 8080, 443, 8443, 16384–32383.
5. **Адрес ngrok не сменился?** При перезапуске он другой — переоформите
   подписку.
6. **Путь именно `/webhooks/max`?** Не `/webhook/max` и не `/webhooks/`.

Если ни один пункт не помог — раздел 5a: long polling снимает все шесть
вопросов разом, потому что входящего адреса в нём нет.

### Опрос идёт, но событий нет

Симптом: `MAX_UPDATES_MODE=polling`, в логах `polling started`, ошибок нет, но
нажатия кнопок до бота не доходят.

Почти наверняка у бота осталась подписка на webhook. Режимы взаимоисключающие:
события уходят на подписку, а опрос возвращает пустоту.

```bash
bash scripts/max-info.sh
```

Раздел «Подписки на webhook» покажет список. Если адрес ваш и больше не нужен:

```bash
curl -X DELETE "https://platform-api2.max.ru/subscriptions?url=https://ваш-старый-адрес/webhooks/max" \
  -H "Authorization: $MAX_BOT_TOKEN"
```

Если адрес чужой — токен общий на несколько команд. Не снимайте подписку
молча, уточните у организаторов.

### POST /webhooks/max отдаёт 404

Это не поломка. При `MAX_MODE=real` и `MAX_UPDATES_MODE=polling` маршрут не
поднимается намеренно: `MAX_WEBHOOK_SECRET` в этом режиме не требуется, значит
проверять подпись было бы нечем, а открытый эндпойнт позволил бы кому угодно
подтвердить чужую регистрацию.

Нужен webhook — верните `MAX_UPDATES_MODE=webhook` и задайте секрет.

### Приходит 401 на webhook

Значение `MAX_WEBHOOK_SECRET` в `.env` не совпадает с тем, что вы передали в
`POST /subscriptions`. Секрет нельзя посмотреть через API — переоформите
подписку с тем значением, которое сейчас в `.env`.

Ещё вариант: reverse proxy вырезает заголовок `X-Max-Bot-Api-Secret`. Проверьте
конфигурацию прокси.

### Сообщение не приходит пользователю

1. `max_user_id` верный? Это числовой ID, а не username.
2. Пользователь открывал диалог с ботом? MAX не даёт писать первым тому, кто
   не начинал общение.
3. Проверьте логи бота: там будет `notification sent` с `message_id` либо
   `max send failed` с описанием.
4. `POST /api/v1/notifications` ответил `422 recipient_unavailable`? Значит,
   MAX отказался доставлять именно этому пользователю: он остановил бота или
   удалил диалог. Пусть откроет бота заново — после `bot_started` сообщения
   снова пойдут.
5. Включён `MAX_MINIAPP_BUTTON=open_app`, а мини-приложение не привязано к
   боту? Верните `link` (раздел 5b).

### Бот узнаёт, что пользователь его остановил

MAX присылает боту `bot_stopped`, когда пользователь останавливает бота, и
`dialog_removed`, когда удаляет диалог. Бот передаёт это в Core Backend
вызовом `POST /max-users/{max_user_id}/bot-status` с `available=false`. На
`bot_started` — тот же вызов с `available=true`. В режиме `CORE_MODE=stub`
эти вызовы видны в `GET /dev/core/actions` как записи `kind: bot_status`, а в
`bash scripts/demo.sh --watch` — строкой «бот НЕ может писать».

### Кнопка «крутится» и не реагирует

Бот не ответил на callback. MAX держит спиннер, пока не придёт
`POST /answers`.

Бот отвечает на **каждой** ветке, включая ошибочные, поэтому спиннер обычно
означает, что webhook вообще не дошёл до бота. Смотрите предыдущие пункты про
webhook.

### В логах `attachment.not.ready`

Временная ошибка MAX при работе с вложениями. SDK повторяет запрос
автоматически. Бот вложений не отправляет, поэтому в норме вы это не увидите.

### 429 Too Many Requests

Слишком много вызовов. Бот классифицирует это как временную ошибку и покажет
пользователю «попробуйте ещё раз». Если это происходит регулярно, добавьте
throttling на стороне Core Backend, который инициирует рассылку.

### Нужно посмотреть, что бот вообще отправляет

Переключитесь в mock и посмотрите журнал — там видны и текст, и payload кнопок:

```bash
curl -s localhost:8080/dev/max/messages | jq '.messages[-1]'
```

Работает только при `APP_ENV=dev` и `MAX_MODE=mock`.

## 9a. TLS и сертификаты

Симптом — одно из двух:

```
curl: (60) SSL certificate problem: unable to get local issuer certificate
x509: certificate signed by unknown authority
```

Это состояние хранилища корневых сертификатов **на вашей машине**, а не
проблема MAX. Важно понимать масштаб: Go использует то же системное
хранилище, что и curl, поэтому если ругается curl — бот в real-режиме тоже
не подключится. Он и не станет: при недоверенном сертификате процесс
отказывается стартовать, потому что повтор здесь не поможет никогда.

Диагностика:

```bash
bash scripts/max-tls-check.sh
```

Скрипт показывает настоящую цепочку сертификатов и называет причину. Токен
ему не нужен.

### Три типичные причины

**Нет или устарел пакет ca-certificates.** Частое состояние свежего WSL и
«тонких» контейнеров. Лечится в одну команду:

```bash
sudo apt update && sudo apt install --reinstall -y ca-certificates
sudo update-ca-certificates
```

**Корень от УЦ Минцифры России.** Российские сервисы всё чаще используют
сертификаты, выпущенные «Russian Trusted Root CA». Этого корня нет в наборе
Mozilla, на котором основан `ca-certificates`, поэтому проверка честно не
проходит. Нужно добавить корень в доверенные — но прежде стоит понимать цену:
**доверенный корневой центр может выпустить сертификат на любой домен**, и
система такому сертификату поверит. Это решение с последствиями за пределами
этого проекта.

Поэтому в боте есть отдельный параметр, сужающий доверие до одного
соединения. Получить и проверить корень проще всего скриптом:

```bash
bash scripts/max-install-ca.sh
```

Он пробует три источника по очереди: официальную раздачу Минцифры, хранилище
сертификатов Windows (в WSL это самый надёжный путь — там корень обычно уже
установлен) и саму цепочку сервера MAX, если та содержит корень. На каждом
шаге проверяется, что получен именно сертификат, а не страница ошибки, — и
если ничего не вышло, скрипт скажет об этом прямо, а не запишет мусор.

Если все источники недоступны, скачайте файл браузером Windows со страницы
<https://www.gosuslugi.ru/crt> и передайте путь скрипту:

```bash
bash scripts/max-install-ca.sh /mnt/c/Users/<вы>/Downloads/russian_trusted_root_ca.cer
```

В `.env`:

```env
MAX_CA_FILE=/полный/путь/к/проекту/certs/russian_trusted_root_ca.pem
```

`MAX_CA_FILE` **добавляет** этот корень к системному набору и действует
**только на соединение с MAX**. Ни Core Backend, ни любой другой HTTPS-вызов
этого доверия не получают.

Это осознанно сделано иначе, чем через переменную `SSL_CERT_FILE`. Та тоже
сработала бы, но действует на весь процесс: доверие, выданное ради MAX,
автоматически распространилось бы на всё остальное — и заметить это потом
было бы непросто. Область действия стоит держать минимальной там, где это
почти ничего не стоит.

Проверка тем же curl (здесь `--cacert` набор заменяет, поэтому файла с одним
корнем достаточно только для этой конкретной проверки):

```bash
curl --cacert certs/russian_trusted_root_ca.pem \
  https://platform-api2.max.ru/me -H "Authorization: $MAX_BOT_TOKEN"
```

### О скачивании корня через `curl -k`

Это слабое место процедуры, и стоит назвать его прямо: сайт распространения
сам закрыт тем же сертификатом, поэтому скачать корень «доверенно» неоткуда —
получается замкнутый круг. `-k` отключает проверку именно на этот один
запрос.

Что стоит сделать после скачивания:

```bash
openssl x509 -in certs/russian_trusted_root_ca.pem -noout -subject -issuer -fingerprint -sha256
```

Убедитесь, что `subject` и `issuer` совпадают (признак корневого
самоподписанного сертификата) и что в них значится Минцифры. Отпечаток стоит
сверить с опубликованным на официальной странице Госуслуг, открытой в
браузере, где корень уже установлен, — это независимый канал.

Косвенная проверка, что вы скачали именно тот корень: цепочка с ним должна
успешно проверяться.

```bash
openssl s_client -connect platform-api2.max.ru:443 \
  -servername platform-api2.max.ru \
  -CAfile certs/russian_trusted_root_ca.pem </dev/null 2>&1 | grep 'Verify return code'
```

Ожидается `Verify return code: 0 (ok)`. Это подтверждает, что корень
соответствует цепочке, но не подменён ли он сам — поэтому отпечаток сверить
всё же стоит.

`certs/` уже добавлен в `.gitignore`: это настройка конкретной машины, а не
часть проекта.

Если всё же нужно доверие на уровне системы (например, чтобы заработали
другие инструменты, а не только бот):

```bash
sudo cp certs/russian_trusted_root_ca.pem \
  /usr/local/share/ca-certificates/russian_trusted_root_ca.crt
sudo update-ca-certificates
```

**Перехват TLS антивирусом или корпоративным прокси.** Kaspersky, ESET и
подобные подменяют сертификаты всех сайтов своим центром. В Windows их корень
обычно установлен, а в WSL — нет, отсюда расхождение: браузер работает,
консоль нет. Скрипт диагностики такой центр распознаёт и называет по имени.
Решение: либо добавить его корень тем же способом, либо отключить перехват
для `platform-api2.max.ru` в настройках защитного ПО.

### Чего делать не стоит

`curl -k` и `InsecureSkipVerify: true` в Go «чинят» симптом, полностью
отключая проверку подлинности сервера. Для разовой диагностики `-k` приемлем
(скрипт выше использует его только чтобы скачать сам корневой сертификат),
но в коде бота этого нет и быть не должно: соединение с подменённым сервером
внешне неотличимо от настоящего, а через него ходит токен бота.

## 10. Чек-лист перед боевым запуском

- [ ] `MAX_BOT_TOKEN` задан и проверен через `GET /me`
- [ ] `MAX_WEBHOOK_SECRET` сгенерирован случайно и совпадает с переданным в `POST /subscriptions`
- [ ] `INTERNAL_API_KEY` изменён с `change-me` (при `APP_ENV=prod` бот иначе не стартует)
- [ ] `APP_ENV=prod` — dev-эндпоинты не регистрируются
- [ ] HTTPS с валидным сертификатом, порт из разрешённого списка
- [ ] Подписка на webhook оформлена, `GET /subscriptions` это подтверждает
- [ ] `/api/v1/*` не опубликован в интернет — только внутренняя сеть
- [ ] `/health` и `/ready` заведены в оркестратор
- [ ] `.env` не в git (проверьте `git status --ignored`)
- [ ] Секретов нет в Docker-образе (конфигурация только через env)
