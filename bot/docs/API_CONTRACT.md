# HTTP-контракт бота

Человекочитаемое описание поверх [`api/openapi.yaml`](../api/openapi.yaml).
Машиночитаемая версия — там; здесь объясняется, почему контракт устроен именно
так и как им пользоваться.

Если вы пишете Core Backend или Mini App, начните с
[INTEGRATION_MINIAPP.md](INTEGRATION_MINIAPP.md) — там тот же контракт в виде
инструкции с диаграммами.

---

## Карта эндпоинтов

| Метод | Путь | Кто вызывает | Аутентификация |
|---|---|---|---|
| POST | `/api/v1/notifications` | Core Backend (сейчас Postman) | `X-Internal-Api-Key` |
| POST | `/webhooks/max` | MAX | `X-Max-Bot-Api-Secret` |
| GET | `/health` | оркестратор | — |
| GET | `/ready` | оркестратор | — |
| GET, DELETE | `/dev/max/messages` | разработчик | — (только `APP_ENV=dev`) |
| GET, DELETE | `/dev/core/actions` | разработчик | — (только `APP_ENV=dev`) |

Три разные группы с тремя разными моделями доступа. Это не случайность:
`/api/v1/*` защищён общим секретом с Core Backend, `/webhooks/*` — секретом,
который знает MAX, пробы открыты, dev-эндпоинты в production просто не
существуют.

---

## Версионирование

Версия в пути: `/api/v1/notifications`.

Что считается ломающим изменением и требует `/api/v2/`:

- переименование или удаление поля;
- изменение типа поля;
- новое обязательное поле;
- изменение смысла значения.

Что можно добавлять в v1:

- новое **необязательное** поле;
- новое значение в `type` (клиенты, которые его не шлют, не заметят);
- новый эндпоинт.

Внутри бота версия живёт в отдельном пакете (`internal/contracts`), и
прикладной слой её не видит. Добавление v2 — это новый файл DTO и новый
маппер; сервисы не меняются.

## POST /api/v1/notifications

### Заголовки

| Заголовок | Обязателен | Описание |
|---|---|---|
| `Content-Type: application/json` | да | |
| `X-Internal-Api-Key` | да | Общий секрет с Core Backend |
| `X-Request-Id` | нет | Ваш correlation ID; если не передан, будет сгенерирован |

### Тело

```json
{
  "request_id": "req_a7f3c9e1",
  "type": "confirmation_required",
  "recipient": { "max_user_id": 123456789 },
  "event": {
    "id": "event_42",
    "title": "Йога в парке",
    "starts_at": "2026-09-22T19:00:00+03:00",
    "address": "Парк Горького",
    "mini_app_url": "https://afisha.example.ru/app/event_42"
  },
  "registration": { "id": "registration_15" },
  "data": {}
}
```

**Неизвестные поля отвергаются** с 400. Опечатка в имени поля должна быть
громкой ошибкой, а не молча потерянным значением.

### Обязательность полей по типам

| Тип | `registration` | `data` |
|---|---|---|
| `registration_created` | обязателен | — |
| `reminder_24h` | обязателен | — |
| `confirmation_required` | обязателен | — |
| `confirmation_retry` | обязателен | — |
| `reminder_1h` | обязателен | — |
| `waitlist_offer` | обязателен | `offer_expires_at` обязателен |
| `event_updated` | не нужен | `changes` **или** `organizer_message` |
| `event_cancelled` | не нужен | — |

Логика простая: `registration` нужен тем типам, чьи сообщения несут кнопки
действий. У отменённого мероприятия подтверждать нечего.

### Ограничения

| Поле | Ограничение |
|---|---|
| `request_id` | ≤ 256 символов, непустое |
| `event.id`, `registration.id` | ≤ 256 символов, **без символа `\|`** |
| `event.title` | ≤ 512 символов |
| `event.address` | ≤ 512 символов |
| `data.organizer_message` | ≤ 2000 символов |
| `data.changes` | ≤ 20 элементов |
| `event.starts_at`, `data.offer_expires_at` | RFC 3339 **со смещением города**; UTC (`Z`, `+00:00`, `-00:00`) отвергается |
| тело целиком | ≤ 64 KiB |

Запрет на `|` — не произвол: идентификаторы попадают в payload кнопки, где `|`
служит разделителем. Отказ на входе лучше, чем битая кнопка у пользователя.

Запрет на UTC — тоже. Бот печатает время в том смещении, в котором оно пришло:
«19:00» в сообщении совпадает с «19:00» на афише в любом городе. По голому UTC
бот не может узнать город, и `2026-09-22T16:00:00Z` превратился бы для
москвича в «16:00» вместо «19:00».

### Ответы

| Код | Когда | Тело |
|---|---|---|
| 202 | Сообщение передано в MAX | `{"request_id","status":"sent","message_id"}` |
| 200 | Дубликат `request_id` | `{"request_id","status":"duplicate","duplicate":true}` |
| 400 | Ошибка валидации | `ErrorResponse` с `details` |
| 401 | Неверный ключ | `ErrorResponse` |
| 413 | Тело > 64 KiB | `ErrorResponse` |
| 422 | MAX отказался доставить этому пользователю: он остановил бота или не открывал диалог | `ErrorResponse`, `recipient_unavailable` |
| 500 | Ошибка внутри бота | `ErrorResponse` |
| 502 | MAX недоступен | `ErrorResponse` |

**422 и 502 требуют противоположных решений.** `502` — MAX недоступен, повтор
может помочь. `422` — MAX работает, но этот пользователь закрыл диалог с
ботом; повтор не поможет, пока он не откроет диалог снова. Core Backend стоит
прекратить повторы и отметить пользователя как недоступного для бота.
`request_id` в обоих случаях освобождается, так что уведомление можно
отправить позже.

**202, а не 200.** Бот принял команду и передал сообщение в MAX. Это не
означает, что пользователь его прочитал, и тем более не означает, что действие
разрешено бизнес-правилами — бот их не проверяет.

## POST /webhooks/max

Этот эндпоинт вызывает MAX. Core Backend его не трогает.

Формат тела задан MAX; описание полей, которые читает бот, — в OpenAPI
(`MaxUpdate`). Обрабатываются `bot_started`, `message_created`,
`message_callback`, а также `bot_stopped` и `dialog_removed`: по ним бот
сообщает Core Backend, что больше не может писать пользователю
(`POST /max-users/{max_user_id}/bot-status`, см. `INTEGRATION_MINIAPP.md`, 6.2).

### Коды ответа — протокольное решение

MAX повторяет доставку при не-2xx. Отсюда правило: **200 на всё, что бот
закончил обрабатывать**.

| Ситуация | Код | Почему |
|---|---|---|
| Событие обработано | 200 | |
| Неизвестный тип события | 200 | Повтор не поможет: бот его никогда не поймёт |
| Неразбираемое тело | 200 | MAX не исправит его повторной отправкой |
| Устаревший payload | 200 | Пользователю уже ответили понятным текстом |
| Дубликат доставки | 200 | Распознан, действие не повторено |
| Неверный секрет | 401 | Доставка нелегитимна |
| Тело > 256 KiB | 413 | |
| MAX недоступен при ответе на callback | 502 | Повтор может помочь |

Ответ 4xx на неизвестный тип события создал бы бесконечный цикл повторов.

### Тело ответа

```json
{ "status": "handled", "update_type": "message_callback", "result": "ok" }
```

`status`: `handled` | `ignored` | `duplicate`.
`result`: `ok` | `ignored` | `duplicate` | `business_error` | `unavailable` |
`bad_payload`.

Это диагностика для разработчика; MAX содержимое тела не использует.

## Формат callback payload

```
v1|<action>|<registration_id>[|<event_id>]
```

| Действие | Код | Кнопка |
|---|---|---|
| Подтвердить участие | `confirm` | «Приду» |
| Отменить запись | `cancel` | «Не смогу прийти», «Отменить запись» |
| Занять место | `wl_accept` | «Занять место» |
| Отказаться от места | `wl_decline` | «Отказаться» |

Примеры:

```
v1|confirm|registration_15|event_42
v1|cancel|registration_15
v1|wl_accept|registration_15|event_42
```

Три свойства, которые стоит знать:

1. **Текст кнопки командой не является.** Payload `Приду` будет отвергнут.
2. **Версия впереди.** Кнопки живут в чатах долго; `v2|...` из будущего
   формата в старом боте будет вежливо отклонён, а не разобран неправильно.
3. **Лимит 1024 байта** задан MAX. Бот проверяет его при формировании кнопки.

Идентичность пользователя в payload **не передаётся**: она берётся из
`callback.user.user_id` в теле webhook. Payload проходит через клиент, и
доверять ему в вопросе «кто это сделал» нельзя.

## Формат ошибок

Один формат на весь API:

```json
{
  "error": {
    "code": "invalid_request",
    "message": "registration.id is required for type \"confirmation_required\"",
    "request_id": "req-9217b3805210af54",
    "details": [
      { "field": "registration.id", "message": "is required for type \"confirmation_required\"" }
    ]
  }
}
```

| `code` | HTTP | Категория |
|---|---|---|
| `invalid_request` | 400 | Ошибка валидации |
| `unauthorized` | 401 | Неверный ключ или секрет |
| `not_found` | 404 | Неизвестный маршрут |
| `method_not_allowed` | 405 | Не тот HTTP-метод |
| `conflict` | 409 | Отказ по бизнес-правилу |
| `payload_too_large` | 413 | Слишком большое тело |
| `upstream_unavailable` | 502 | MAX или Core Backend недоступны |
| `recipient_unavailable` | 422 | Пользователь остановил бота или не открывал диалог |
| `internal_error` | 500 | Ошибка внутри бота |

`upstream_unavailable` намеренно отделён от `internal_error`: первый имеет
смысл повторить, второй — нет. Для вызывающей стороны это разные решения.

`details` заполняется только при валидации и содержит **все** проблемные поля
сразу, отсортированные по имени. Заставлять исправлять по одному полю за
круг — плохой способ изучать контракт.

`message` предназначен разработчику. Внутренние Go-ошибки в него не попадают:
они уходят в логи, где им и место.

## Идемпотентность

`request_id` — ключ. Повтор возвращает `200` и `"duplicate": true`, второе
сообщение не отправляется.

Реализация — map в памяти с TTL 30 минут по умолчанию. **Не переживает
рестарт и не разделяется между репликами.** Ограничение осознанное: у бота нет
собственных бизнес-данных, ради которых стоило бы поднимать Redis. Интерфейс
`idempotency.Store` готов к другой реализации, когда появится вторая реплика.

Рекомендация: генерируйте `request_id` детерминированно для логически одного
уведомления, например `notif_{registration_id}_{type}_{scheduled_at}`.

Входящие webhook дедуплицируются по `callback_id` тем же механизмом.

---

## Correlation ID

- `X-Request-Id` на входе используется как есть (до 128 символов);
- если не передан — генерируется `req-<hex>`;
- возвращается в заголовке ответа и в теле ошибки;
- попадает во все логи по этому запросу;
- передаётся дальше в Core Backend при вызове его эндпоинтов.

## Аутентификация: три разных секрета

| Секрет | Направление | Заголовок |
|---|---|---|
| `INTERNAL_API_KEY` | Core Backend → Bot | `X-Internal-Api-Key` |
| `CORE_API_KEY` | Bot → Core Backend | `X-Api-Key` |
| `MAX_WEBHOOK_SECRET` | MAX → Bot | `X-Max-Bot-Api-Secret` |

Их легко перепутать, и каждая путаница — дыра в безопасности. Сравнение
выполняется за константное время: наивное `==` утекает материал ключа через
тайминг ответа.

## Пробы состояния

### GET /health — liveness

Процесс жив. Никакого сетевого ввода-вывода: недоступность MAX или Core
Backend не должна приводить к перезапуску исправного бота.

```json
{ "status": "ok", "version": "1.0.0", "uptime_seconds": 3600 }
```

Всегда 200, если процесс отвечает.

### GET /ready — readiness

Проверяет зависимости, таймаут 3 секунды.

```json
{
  "status": "ready",
  "dependencies": [
    { "name": "max",  "mode": "real", "status": "ok" },
    { "name": "core", "mode": "http", "status": "ok" }
  ]
}
```

В `MAX_MODE=real` выполняет `GET /me` к MAX: недействительный токен — именно
та ошибка конфигурации, ради которой эта проба существует. В `CORE_MODE=http`
вызывает `GET {CORE_BASE_URL}/health`.

При проблеме — `503` и `"status": "error"` с кратким описанием. Секреты в этот
вывод не попадают.

## Dev-эндпоинты

Только при `APP_ENV=dev`. В production маршруты **не регистрируются** — это
сильнее, чем «закрыты»: эндпоинт, которого нет, нельзя прощупать на предмет
его существования.

Дополнительно: `/dev/max/messages` существует только при `MAX_MODE=mock`, а
`/dev/core/actions` — только при `CORE_MODE=stub`. Иначе инспектировать
нечего.

| Эндпоинт | Метод | Действие |
|---|---|---|
| `/dev/max/messages` | GET | Что бот «отправил» в MAX: текст, формат, кнопки с payload |
| `/dev/max/messages` | DELETE | Очистить журнал |
| `/dev/core/actions` | GET | Что бот передал бы в Core Backend |
| `/dev/core/actions` | DELETE | Очистить журнал |

Оба буфера ограничены 500 записями: это инструмент отладки, а не журнал
аудита. Production-код к ним не обращается.

## Проверка соответствия документации коду

В `internal/transport/http/openapi_contract_test.go` лежат тесты, которые
сверяют `api/openapi.yaml` и `.env.example` с реальным кодом:

- каждый маршрут из роутера описан в OpenAPI;
- каждый путь из OpenAPI существует в роутере;
- перечисление типов уведомлений совпадает с `domain.AllNotificationTypes()`;
- имена заголовков в документе совпадают с константами;
- `.env.example` покрывает все читаемые переменные и не содержит настоящих
  секретов.

Документация, описывающая несуществующий эндпоинт, ломает сборку. Это дешевле,
чем обнаруживать расхождение на интеграции.
