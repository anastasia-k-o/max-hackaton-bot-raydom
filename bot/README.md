# MAX Bot — модуль чат-бота для каталога бесплатных мероприятий

Go-сервис, который присылает пользователям мессенджера MAX напоминания о
мероприятиях и принимает их ответы по кнопкам.

Главное, что нужно понять про этот модуль: **бот не является источником истины**.
Он не решает, есть ли свободные места, можно ли отменить запись и кто следующий
в листе ожидания. Он получает команду «уведомить пользователя», формирует
сообщение с кнопками, отправляет его в MAX, а нажатие кнопки возвращает обратно
в Core Backend. Все бизнес-решения принимает Core Backend.

Ни Mini App, ни Core Backend, ни ML-модуль пока не существуют. Поэтому проект
устроен так, чтобы **сейчас** его можно было целиком показать через Postman на
заглушках, а **потом** перейти на реальные системы сменой конфигурации, а не
переписыванием кода.

---

## Быстрый старт

Нужен только Go 1.24+. Токен MAX, база данных и интернет не требуются.

```bash
git clone <repo> && cd hackatonBotMAX
cp .env.example .env
make run
```

Бот поднимется на `http://localhost:8080`. Проверка, что всё живо:

```bash
curl localhost:8080/health
```

Полный цикл — уведомление, нажатие кнопки, обновление сообщения — одной
командой:

```bash
make smoke
```

Скрипт поднимает бота на отдельном порту, проходит весь сценарий и печатает
результат каждого шага. Если он зелёный, окружение настроено верно.

## Что это делает

Бот отправляет восемь типов сообщений:

| Тип | Сообщение | Кнопки |
|---|---|---|
| `registration_created` | ✅ Вы записаны | Открыть афишу · Отменить запись |
| `reminder_24h` | ⏰ Напоминание | Открыть афишу · Не смогу прийти |
| `confirmation_required` | ❓ Подтвердите участие | Приду · Не смогу |
| `confirmation_retry` | ❓ Подтвердите участие (повторно) | Приду · Не смогу |
| `reminder_1h` | 📍 Скоро начало | Маршрут · Не смогу прийти |
| `waitlist_offer` | 🔥 Освободилось место | Занять место · Отказаться |
| `event_updated` | ⚠️ Мероприятие изменено | Открыть афишу |
| `event_cancelled` | ❌ Мероприятие отменено | Открыть афишу |

Когда пользователь нажимает кнопку, бот передаёт действие в Core Backend и
заменяет сообщение результатом — например, «✅ Участие подтверждено» уже без
кнопок, чтобы повторное нажатие не вызвало второе действие.

Чего бот **не** делает и делать не будет: каталог мероприятий, поиск, фильтры,
рекомендации, регистрация пользователей, создание мероприятий. Всё это живёт в
мини-приложении.

## Архитектура в двух словах

```
Mini App → Core Backend → [ Bot ] → MAX Bot API → пользователь
пользователь → MAX Webhook → [ Bot ] → Core Backend
```

Внутри бота — два порта (интерфейса), у каждого по две реализации:

```
        MaxClient                      CoreGateway
            ▲                               ▲
     ┌──────┴──────┐                 ┌──────┴──────┐
  MockMAX       RealMAX          StubCore     HTTPCore
 (в памяти)   (MAX Bot API)     (в памяти)   (Core Backend)
```

Какая реализация подключится, решают две переменные окружения — `MAX_MODE` и
`CORE_MODE`. Прикладной код (`internal/app`) о них не знает вовсе: он написан
против интерфейсов. Именно поэтому переход с заглушек на боевые системы — это
правка `.env`, а не рефакторинг.

Подробности, диаграммы и обоснование решений: **[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)**.

### Структура проекта

```
cmd/bot/                 точка входа; единственное место, где выбираются адаптеры
internal/
  config/                загрузка и валидация конфигурации
  domain/                платформонезависимая модель: сообщения, действия, уведомления
  contracts/             версионированные DTO публичного HTTP API + формат ошибок
  callback/              кодек payload кнопок (v1|action|id)
  render/                все пользовательские тексты и сборка сообщений
  app/                   прикладные сервисы: NotificationService, BotService
  core/                  порт CoreGateway
    stub/                  реализация в памяти
    httpgw/                реализация поверх HTTP
  maxapi/                порт MaxClient + разбор Update от MAX
    mock/                  реализация в памяти
    real/                  обёртка над официальным Go SDK
  transport/http/        HTTP-адаптер: роутер, middleware, тонкие handlers
  transport/polling/     входящий адаптер long polling (альтернатива webhook)
  idempotency/           защита от повторной доставки
  observability/         структурное логирование и correlation ID
api/openapi.yaml         контракт для команды Mini App/Core Backend
postman/                 готовая к импорту коллекция и окружение
scripts/smoke.sh         дымовой тест полного цикла
docs/                    документация
```

## Режимы работы

### Mock mode — по умолчанию

```env
MAX_MODE=mock
CORE_MODE=stub
```

Токен не нужен, наружу ничего не уходит. Отправленные сообщения пишутся в
память MockMAX, действия пользователя — в память StubCoreGateway. Смотреть
их можно через dev-эндпоинты:

```bash
curl localhost:8080/dev/max/messages    # что бот «отправил» в MAX
curl localhost:8080/dev/core/actions    # что бот передал бы в Core Backend
```

Эти маршруты регистрируются только при `APP_ENV=dev`. В production их не
существует — не «закрыты», а именно не зарегистрированы, и отдают обычный 404.

### Real MAX mode

```env
MAX_MODE=real
MAX_BOT_TOKEN=<токен от @MasterBot>
MAX_WEBHOOK_SECRET=<придуманный вами секрет>
CORE_MODE=stub
```

Бизнес-код не меняется. При старте бот выполняет `GET /me` и, если токен
недействителен, **отказывается стартовать** с понятной диагностикой вместо
того, чтобы молча работать со сломанной конфигурацией.

Пошагово — получение токена, регистрация webhook, требования к HTTPS и портам,
troubleshooting: **[docs/MAX_SETUP.md](docs/MAX_SETUP.md)**.

### Long polling — когда публичного адреса нет

```env
MAX_MODE=real
MAX_BOT_TOKEN=<токен от @MasterBot>
MAX_UPDATES_MODE=polling
```

Webhook требует, чтобы MAX мог постучаться к нам, то есть публичный
HTTPS-адрес. На ноутбуке за NAT его нет, и обычный выход — туннель (ngrok,
cloudflared): сторонний сервис, аккаунт и ещё одна точка отказа.

В режиме `polling` бот сам открывает соединение к MAX и держит его, ожидая
событий. Публичный адрес, туннель и `MAX_WEBHOOK_SECRET` не нужны.

Режимы **взаимоисключающие**: по схеме MAX метод `GET /updates` предназначен
для бота, не подписанного на webhook. Бот проверяет подписки при старте и
предупреждает, если они есть.

Поведение самого бота от выбора транспорта не зависит: оба адаптера вызывают
один и тот же `BotService.HandleUpdate` с одним и тем же разобранным событием,
и это проверяется тестом, который подаёт одно событие обоими путями и
сравнивает результат.

Подробности: [docs/MAX_SETUP.md](docs/MAX_SETUP.md), раздел 5a.

### Как протестировать без мини-приложения и Core Backend

Ни то, ни другое для проверки бота не нужно, и это не компромисс, а следствие
архитектуры: бот — адаптер, и обе стороны от него отделены интерфейсами.

```bash
make run                          # в одном терминале
bash scripts/demo.sh <max_user_id>  # в другом
```

Скрипт играет роль Core Backend и шлёт все восемь типов уведомлений подряд,
печатая для каждого, что должно прийти в MAX. Ваш `max_user_id` видно в логах
бота, как только вы напишете ему что-нибудь в мессенджере; скрипт запомнит его
в `.env`.

Мероприятия в прогоне взяты из моков мини-приложения (`event_1`…`event_14`):
если мини-приложение запущено и `MINI_APP_URL` указывает на него
(`https://<хост>/app`), «Открыть афишу» ведёт на ту же карточку.

Мини-приложение при этом не требуется: при пустом `MINI_APP_URL` кнопка-ссылка
просто не добавляется, остальное сообщение не меняется.

Как кнопка открывает мини-приложение — обычной ссылкой в браузере или внутри
MAX (`MAX_MINIAPP_BUTTON=open_app`) — см. [docs/MAX_SETUP.md](docs/MAX_SETUP.md),
раздел 5b.

Обратное направление — то, что бот передал бы в Core Backend при нажатии кнопок:

```bash
bash scripts/demo.sh --watch
```

Пока `CORE_MODE=stub`, эти вызовы никуда не уходят и складываются в память.
Когда Core Backend появится, `CORE_MODE=http` и `CORE_BASE_URL` переключат их на
настоящие HTTP-запросы, и код бота при этом не изменится.

### Подключение настоящего Core Backend

```env
CORE_MODE=http
CORE_BASE_URL=https://api.afisha.example.ru/v1
CORE_API_KEY=<ключ>
```

`BotService` при этом не меняется ни на строку. HTTP-адаптер уже написан и
покрыт тестами против `httptest.Server`, включая обработку 4xx, 5xx и таймаутов.

ошибок.

## HTTP API

| Метод | Путь | Кто вызывает | Аутентификация |
|---|---|---|---|
| POST | `/api/v1/notifications` | Core Backend (сейчас Postman) | `X-Internal-Api-Key` |
| POST | `/webhooks/max` | MAX | `X-Max-Bot-Api-Secret` |¹
| GET | `/health` | оркестратор | — |
| GET | `/ready` | оркестратор | — |
| GET/DELETE | `/dev/max/messages` | разработчик | — (только `APP_ENV=dev`) |
| GET/DELETE | `/dev/core/actions` | разработчик | — (только `APP_ENV=dev`) |

¹ При `MAX_MODE=real` и `MAX_UPDATES_MODE=polling` этот маршрут не
поднимается и отдаёт 404: секрет в этом режиме не требуется, значит проверять
подпись было бы нечем, а открытый эндпойнт позволил бы кому угодно подтвердить
чужую регистрацию.

`X-Internal-Api-Key` и `X-Max-Bot-Api-Secret` — **разные механизмы**. Первый
защищает наш API от посторонних вызовов, второй подтверждает, что webhook
пришёл от MAX. Путать их нельзя.

Машиночитаемый контракт: [`api/openapi.yaml`](api/openapi.yaml).
Человекочитаемое описание: [docs/API_CONTRACT.md](docs/API_CONTRACT.md).

## Конфигурация

Все переменные с комментариями — в [`.env.example`](.env.example). Минимум для
запуска:

```env
APP_ENV=dev
HTTP_PORT=8080
MAX_MODE=mock
MAX_UPDATES_MODE=webhook
CORE_MODE=stub
INTERNAL_API_KEY=change-me
LOG_LEVEL=debug
```

Конфигурация проверяется при старте, и все проблемы сообщаются сразу, а не по
одной на перезапуск. Секреты никогда не попадают в логи: при старте печатается
`<set>` или `<empty>`, а не значение.

## Разработка

```bash
make help          # список команд
make run           # запустить локально
make test          # тесты
make test-race     # тесты с детектором гонок
make test-cover    # покрытие, отчёт в coverage.html
make vet           # go vet
make lint          # golangci-lint, если установлен; иначе go vet
make build         # бинарник в bin/
make smoke         # дымовой тест полного цикла
make check         # fmt + vet + test перед коммитом
```

`golangci-lint` не входит в зависимости. Установка, если нужен:

```bash
go install github.com/golangci/golangci-lint/cmd/golangci-lint@latest
```

### Что покрыто тестами

Кодек callback-payload (table-driven, включая round-trip и враждебные
значения), рендерер всех восьми типов сообщений, валидация контракта,
`BotService` и `NotificationService`, оба middleware аутентификации, HTTP-слой
целиком через `httptest`, `HTTPCoreGateway` против `httptest.Server` (успех,
4xx, 5xx, таймаут), адаптер MAX против подменного сервера, загрузка
конфигурации и защита от дублей.

Отдельный набор тестов сверяет `api/openapi.yaml` и `.env.example` с кодом:
маршрут, который есть в документации, но не в роутере (или наоборот), ломает
сборку. Это защита от документации, описывающей несуществующие эндпоинты.

**Реальные вызовы MAX API в автоматических тестах не выполняются.**

## Docker

```bash
cp .env.example .env
make docker-build
make docker-up
make docker-logs
```

Multi-stage сборка, статический бинарник, запуск от непривилегированного
пользователя, healthcheck, конфигурация только через переменные окружения.
Секретов внутри образа нет.

В `docker-compose.yml` намеренно нет PostgreSQL, Redis и брокеров сообщений:
бот не владеет бизнес-данными, и добавлять инфраструктуру ради MVP не нужно.

## Известные ограничения

Названы явно, чтобы никто не наткнулся на них в неподходящий момент.

1. **Защита от дублей живёт в памяти процесса.** Не переживает рестарт и не
   разделяется между репликами. Для хакатона этого достаточно; интерфейс
   `idempotency.Store` готов к реализации поверх Redis, если появится вторая
   реплика.
2. **Scheduler не реализован.** Уведомления инициируются снаружи — сейчас
   Postman, потом Core Backend. Точка расширения описана в ARCHITECTURE.md;
   рекомендуемый вариант — планировщик на стороне Core Backend.
3. **Core Backend ещё не существует.** `HTTPCoreGateway` написан против
   контракта из [docs/INTEGRATION_MINIAPP.md](docs/INTEGRATION_MINIAPP.md) и
   покрыт тестами, но с живым backend не проверялся.
4. **Буферы MockMAX и StubCore ограничены** 500 записями каждый. Это
   инспекционные буферы, а не журнал аудита.
5. **Локализация — только русский.** Все тексты собраны в
   `internal/render/texts.go`; второй язык потребует превратить одну структуру
   в map по локали, но полноценный i18n-фреймворк сознательно не строился.
6. **`open_app`-кнопки не используются.** Для них нужен идентификатор бота,
   привязанного к мини-приложению; пока вместо них обычные ссылки.
